### 読んだ問題の要約

#### ① `pytest-dev__pytest-5413`
- **問われている内容**: `with pytest.raises(...) as excinfo:` で捕捉した例外オブジェクト `excinfo` に対して `str(excinfo)` を呼び出した際、通常の Python の `str(e)` のように例外メッセージ全体が返らず、エラー発生箇所のファイルパスと行番号、メッセージの1行目だけが返ってしまう仕様（バグ）の修正。`ExceptionInfo.__str__` の挙動を見直し、直感的なメッセージ表現を返すように変更することが求められる。
- **自分なら解けるか**: 解けない
- **LLM にとって何が難しいか**: エラーメッセージ全体が全体が返ってこないことから，原因を特定するために，原因箇所まで遡りながら対策を考えること

#### ② `scikit-learn__scikit-learn-13496`
- **問われている内容**: `IsolationForest` クラスに `warm_start` パラメータが公開されておらず、ベースクラス（`BaseBagging`）が持つ「木を追加学習する機能」を利用できない不備の改善。`__init__` に `warm_start=False` を追加し、親クラスへ渡すとともにドキュメントを更新する。
- **自分なら解けるか**: `IsolationForest` クラスを見返すのと，親クラスを見返すことで原因は特定できそう
- **LLM にとって何が難しいか**: プロジェクト自体の思想に反しないようなコードを記述し修正すること

#### ③ `sympy__sympy-13146`
- **問われている内容**: 指数部分に浮動小数点数（例：`x**2.5`）を含むシンボリックな数式同士を引き算（`expr1 - expr2`）して `simplify()` を実行した際、本来 `0` に簡約されるべき式が `0` にならず残ってしまうバグの修正。
- **自分なら解けるか**: 解けない（何が原因なのかが見当もつかない）
- **LLM にとって何が難しいか**: 原因の特定だけではなく，演算処理に関する知識が必要になるのと，修正した結果，他の箇所に影響が出るのかも考慮する必要がある点

#### ④ `astropy__astropy-12907`
- **問われている内容**: 複合モデル（CompoundModel）の分離可能性（separability）を計算する `separability_matrix` 関数において、ネストされた複合モデルを渡した際に正しい行列が返らず、誤った依存関係が計算されてしまうバグの修正。
- **自分なら解けるか**: この領域におけるドメイン知識がないことから厳しい
- **LLM にとって何が難しいか**:行列演算の確認だけではなく，依存関係の修正が求められることから，修正後に副作用が出ないか確認しながら進める点

### 作成の人数と手順、および採点方法

#### 作問・検証の人数と手順
1. **元のタスク収集**: Princeton NLP チームが、実際の人気 Python オープンソースリポジトリから、実際の GitHub Issue とそれを解決した Pull Request（PR）のペア 2,294 件を収集。
2. **検証者の規模と立場**: OpenAI が93名の経験豊富な Python ソフトウェア開発者を招集して検証を実施。
3. **検証プロセス（1 件あたり 3 名体制）**:
   * 元の SWE-bench から抽出した 1,699 件のサンプルに対し、各タスクを3名の独立した開発者がレビュー。
   * 「Issue の記述だけで解決すべき要件が明確に分かるか」「テストケースは公平で、正しい修正だけを合格させるか」などの基準で評価。
4. **フィルタリング結果（何件落としたか）**:
   * レビューした 1,699 件のうち、3 名全員（または厳格な合意基準）が「問題なし（仕様が明確でテストも妥当）」と認めた 500 件のみを採用し、残りの 1,199 件（約 70%）を除外した。
   * 除外された主な理由は「仕様の曖昧さ」「テストの過剰適合」「環境構築の不具合」であった。

#### 採点手法
* **完全自動化された実行ベース評価（Execution-based Evaluation）**:
  * LLM による主観採点や文字列の完全一致（BLEU 等）は一切使わない。
  * モデルが生成した修正パッチ（`git diff`）を、隔離された Docker コンテナ内の該当リポジトリに適用し、実際の単体テストスイート（pytest / Django test runner 等）を実行する。
  * その Issue を修正するために書かれた **FAIL_TO_PASS テスト**（修正前は失敗し、修正後に成功すべきテスト）と、既存機能を壊していないかを確認する **PASS_TO_PASS テスト**（回帰テスト）の **すべてに合格した場合のみ「正解（Resolved）」** と判定される。

### 今日の評価セットとの違い

今日の評価セットとは、そもそも評価対象が大きく異なる。特に、今回の例では、モデルが問題を解くパターンではなく、出力した回答の正誤判定が評価セットになっている。
さらに、データセットを作成する上で、厳格なフィルタリングをかけていないことも違いと言えると考える。

- 気づき・疑問：

小規模な独自評価セットは「手早く仮説検証を回す」のには最適だが、作成者のバイアスや問題の曖昧さが混入しやすい。一方でフロンティアモデルの性能指標として使われるベンチマークは、**「問題そのものの不備（ノイズ）を取り除くための人間による多重レビュー」**と、**「採点のブレをゼロにするための決定論的なテスト環境」**に膨大なコストが投じられていることが分かった。
